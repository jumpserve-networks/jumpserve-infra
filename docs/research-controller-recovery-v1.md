# Qualified operational research controller releases

The platform supervisor's v1.2 policy adds an operational release adapter. It
preserves the protected-file policy for generated coding tools. The trusted
broker alone derives approval metadata and a runtime pin after qualification.

The adapter covers controller housekeeping, original-dispatch reconciliation and
inspection-identifier validation. An AST comparison freezes the rest of the
declared runtime, including model request construction, scientific phase and
coverage checks, prompts, policies, dependencies and experiment executors. Every
existing research test must remain byte-identical. New regression tests belong
in new files. Unsupported changes retain an explicit separate-qualification
blocker; this adapter is not a general scientific-method release mechanism.

The broker obtains the predecessor from its exact Git revision and verifies all
manifest hashes and prior qualification. It runs the fixed backend checks plus
the installed operational checks in a read-only, network-free container without
cloud or publisher credentials. It persists a source-bound certificate and raw
check outputs in private Supabase artifacts. Model qualification is inherited
only because the protected request/scientific content is unchanged; this profile
makes zero evaluation-provider calls and does not claim independent scientific
review.

The tool image pins an Ubuntu 24.04 amd64 manifest and explicitly installs
Python 3.12 in a virtual environment, matching the production controller minor
version. The build asserts that version. The first AWS rehearsal retained four
unchanged-test failures from the older Python 3.10 image's UTC timestamp parser;
those failures are evidence of environment mismatch, never permission to change
the tests or scientific code.

The tested source and derived approval go through an exact-head, protected backend
PR. After merge, the broker generates an infrastructure PR containing only the
new runtime manifest and a public certificate of hashes and software checks.
Both PRs require strict Platform validation. Main advancement before merge
restarts qualification; derived pins can be rebased only while their predecessor
is unchanged and no deployment intent has been dispatched. Every superseded
source, artifact and operation remains recorded.

`research-runtime-release.yml` checks the same source independently in isolated
containers before acquiring GitHub OIDC credentials. It requires current main
revisions and the exact certificate/profile, then starts from the actual settled
BenchmarkStack template. Only Code and matching asset metadata for the three
existing research controllers change. Configuration, IAM, parameters, outputs,
experiment executors and published Lambda versions retain their deployed values.
Verification reads the settled template and downloads all three actual Lambda
ZIPs, checking every file and ZIP checksum against the manifest. A dispatched
workflow is never treated as a successful deployment.

Verified backend and infrastructure-pin release receipts are recorded in
Supabase and exposed through the existing private Platform Updates dashboard.
`research_runtime_resume` then considers known UUID-validation and expired-lease
planning stops. Under the original advisory lock it requires the verified
production proof and matching pin, current category limits, original deadlines,
active authorization and settled provider/experiment identities. It queues each
task at most once per source binding and preserves context, labels, counters,
commitments, scientific criteria and original evidence. Unknown calls remain
fenced. This is operational progress, never a successful scientific finding.

For initial activation, apply migrations 004/005, install the source-qualified
v1.2 supervisor on the existing AWS host, and append the new immutable policy
authorization. A service-only `runtime_reviewed_source` checkpoint can hand the
broker an exact already-reviewed backend main revision for initial qualification.
It is not accepted from model output or a paper. Future eligible source repairs
enter the adapter directly after their fixed checks pass. No workstation,
interactive AWS login or paid-provider fallback is required.
