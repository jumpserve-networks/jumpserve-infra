# Claim experiment design v1

Frozen implementation and evaluation scope: 2026-10-17, before candidate model calls.

Question: can an authenticated researcher turn any recorded paper claim into a
source-bound experimental proposal and resolve its missing inputs before execution?
This is a software workflow evaluation, not validation of the scientific claims.

The retained-plan path stays intact. An unmatched current gap creates one stable,
owner-private paper follow-up bound to the original claim, source and gap bytes.
Planning reuses versioned packets, scoped sessions, fresh comprehension/critic
reviews and the existing queue. Paper claims remain published-paper claims; no
unpublished-proposal source is substituted. Hypothesis text and known source hashes
are enforced against the retained context. A proposal is never a measurement.

Release blockers: authorization and stale-gap tests; idempotent initialization;
immutable context/packet/raw model bytes and hashes; bounded contexts and model
calls; unavailable dependencies remain explicit; no model execution tool; source
instruction resistance; protocol and current-review gates before freeze/enqueue;
registered networking specifications only for automatic jobs; desktop/mobile
missing, failed and complete planning states; build and relevant regressions.

Prompt candidate: research-claim-design-v1 in a separate prompt module. Existing
idea review prompt v11 remains unchanged. Development cases are: networking
comparison, missing dataset, unavailable equipment, causal overreach, unit
ambiguity, source injection, absent source hash, and a complete emulated pilot.
Every actual answer must preserve the claim, distinguish proposals from results,
state missing inputs honestly, propose a relevant comparison and falsification
criterion, preserve units/dependence/coverage and avoid executable placeholders.
For the injection case it must ignore instructions within source fields.
All eight cases must pass both schema checks and documented AI inspection before
publication; AI inspection is not human or independent scientific review.

At most eight development calls per candidate, 4096 output tokens per call,
24 KB context, temperature zero, no automatic retries. Original SDK responses,
failed attempts, tokens and wall time must be retained. Charges unavailable from
the provider remain null. Reused/tuned cases are development regressions, never
held-out validation. No held-out performance claim is planned.

Conditional production checks: migration application to verified Supabase project,
prompt actual-answer evaluation/publication, runtime deployment, and legitimate
authenticated browser-to-model-to-queue request. No production deployment is
authorized by this implementation turn. Local fixtures cannot establish live
scientific or model performance. Unsupported domains may yield explicit operator
tasks; neither a design nor queueing changes an existing scientific assessment.
