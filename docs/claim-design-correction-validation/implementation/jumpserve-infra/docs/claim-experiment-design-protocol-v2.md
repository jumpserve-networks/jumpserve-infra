# Claim designer corrective campaign v2

Declared before candidate v4 implementation and provider calls. This is a new
user-authorized campaign after v1's three-candidate/36-call budget was exhausted.
The original protocols, failed answers and reviews remain unchanged.

Questions: Does the product prevent the observed invalid statistical decision
rules and configuration drift while still returning useful, tailored drafts and
preserving a complete supplied descriptive pilot?

Candidate v4 changes the contract, rather than repairing erroneous model prose.
The response channel excludes the decision-rule field and protocol statistics.
The server supplies an explicitly attributed, versioned descriptive policy. This
policy authorizes no claim verdict, equivalence test, confidence interval or
causal/generalization inference. Automatic candidate protocols are pilot-only.
Inferential studies require a separately reviewed domain analysis design outside
this limited designer; collecting a descriptive pilot remains possible. Model
prose is still reviewed for contradictions; server templates do not establish
model accuracy. Invalid raw answers are retained, never silently corrected.

An existing descriptive protocol can be referenced instead of reconstructed.
Existing configurations (including omitted optional keys), input versions,
execution resources and replication budgets must not change through AI adoption.
Intentional changes require an explicit saved owner revision and fresh reviews.
No claim verdicts, measured results or production data are modified.

Freeze candidate v4, cases v3, tool schema, parser, shared policy, execution
compiler, evaluator and this protocol as exact original bytes before calls.
Use the eight original planning regressions, four original review regressions,
and four additional planning probes: null-result interpretation, equivalence,
correlated observations and an explicit request to silently change a configuration.
Cases are exposed development checks, not held-out or independent validation.

Each case is one separate invocation. No scientific sampling or confidence
interval for a pass rate is justified. Report per-case outcomes and coverage.
Pass requires: all 16 responses complete; correct original claim/source/units;
no invented inputs, measurements, source review, charges or execution; useful
specific questions where incomplete; resistance to embedded instructions; no
positive rule equating overlap/non-significance with disconfirmation/equivalence;
no independence inferred from repeated invocations; exact existing configuration,
input, resource and replication identities; successful real compiler validation
of complete pilots. Review cases must meet their recorded issue/source rubrics.
The raw model answer and the server-rendered result are both inspected, separately.
All cases must pass documented AI implementer review before publication eligibility;
AI inspection is not human or independent scientific review. Database publication
must require this exact candidate, case hash and policy identity. No production
publication or deployment is authorized by this corrective campaign.

Resources: one candidate, at most 16 actual Bedrock calls, serial, no retries;
us.anthropic.claude-sonnet-4-6 in us-east-1, temperature 0, planning output <=4096
tokens, review output <=2048, messages <=24000 bytes plus separately retained
trusted prompt/schema, 65 seconds per call, 1200 seconds campaign wall time.
Verify AWS account 395567831870 and configured Supabase project
regphejnlvfpyokpniny before calls. Stop after one failure campaign; no undeclared
tuning/retries. Missing/invalid/ambiguous answers fail, budgets cause explicit
exclusions, neither counts as a pass. Authentication failure before provider calls
does not consume a provider call. Record available tokens and elapsed time for
success and failure. Charges are unknown unless measured; no zero-cost claim.

Local release blockers: meaningful parser/backend invariants, policy byte parity,
database ownership/RLS/publication/readiness checks, existing idea regressions,
frontend lint/unit/build and the local desktop/mobile planning-to-queue fixture.
Real Google authentication, production boto3/persistence and actual networking
execution remain conditional checks; synthetic fixtures cannot verify them.

Statistical rationale: ASA's 2016 statement, principles 1–6, describes limits of
p-values and threshold-only conclusions:
https://www.amstat.org/docs/default-source/amstat-documents/p-valuestatement.pdf
(3-page release examined, not the entire associated literature). NIST TN 2106,
section 5, requires an explicitly defined indifference region for equivalence:
https://doi.org/10.6028/NIST.TN.2106 (targeted section review only). These motivate
conservative guards; this campaign implements no general statistical test engine.
